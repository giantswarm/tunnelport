# CI-runnable E2E harness

Status: done
Type: HITL

## What to build

Automate the slice-3 smoke test as a CI job that runs on every PR and
on `main`. Spins up kind, installs Teleport (or connects to a cloud
test tenant), provisions sample `TeleportBot`/role/token, deploys the
operator chart from slice 6, applies a sample `RemoteApp`, waits for
`status.ready=true`, runs a curl-pod assertion against the rendered
Service, asserts the response matches the producer app, then tears
down.

The HITL coordination required:

- Decide which Teleport instance backs CI (cloud test tenant credentials
  in CircleCI context, or a locally-run Teleport binary started inside
  the CI job).
- CI infrastructure: **CircleCI + the `architect` orb**, per GS
  convention (see `docs/gs-operator-conventions.md`). The
  `.github/workflows/` directory in GS operator repos contains only
  `zz_generated.*` files owned by `devctl`; real CI is in
  `.circleci/config.yml`. Cluster-tier e2e via Tekton
  (`cluster-test-suites`) is a separate concern that may slot in
  later — out of scope for this slice.
- Decide how the `TeleportBot`/role/token are provisioned each run
  (idempotent script via Teleport API, or pre-provisioned and reused).

Reuses the manifests, runbook, and curl-pod assertion from slice 3 —
this slice is the wrapping that makes them runnable headlessly.

## Acceptance criteria

- [ ] CI job green on a clean main branch
- [ ] CI job red when the smoke flow is intentionally broken (e.g. invalid token Secret)
- [ ] Job runs in under ~10 minutes end-to-end
- [ ] No persistent state between runs — each run provisions and tears down
- [ ] Documented in `hack/smoke/README.md` how to run the same flow locally for debugging
- [ ] Test Teleport credentials stored as CI secrets (not committed)

### Closed

> *This was generated by AI during slice-7 implementation.*

Wrapped the slice-3 runbook into a single-shot script
(`hack/smoke/run.sh`) that brings up three kind clusters in
parallel, builds and loads the operator image, provisions the
Teleport role/bot/tokens via `tctl exec`, deploys the operator
chart, applies a sample `RemoteApp`, waits for
`status.ready=true`, runs the curl assertion against the
rendered Service, and asserts the response body matches
`hello-from-producer`. A bash `trap` ensures kind clusters and
tmp files are torn down on every exit path; on failure, the trap
also dumps pod state and tbot/kube-agent logs from all three
clusters before tearing down.

The script wired into `.circleci/config.yml::e2e-smoke` as a
`machine` executor job (kind requires real Docker, not the
remote-docker shim). The job runs after `architect/go-build` and
gates `architect/push-to-registries`, so a red smoke blocks the
release path. `no_output_timeout: 12m` matches the script's
internal step timeouts so a stuck step fails the job, not
CircleCI's outer wall-clock.

Locally verified end-to-end: `hack/smoke/run.sh` ran clean from
empty Docker to "✅ SMOKE PASSED" in under 4 minutes on a
developer laptop, then tore everything down.

**HITL items resolved by self-contained design:**
- Tenant choice — the smoke uses local kind Teleport, no shared
  GS tenant, no CI secret context.
- TeleportBot/role/token provisioning — idempotent via `tctl
  bots add` and `tctl create -f` execs against the in-cluster
  auth pod. No persistent state between runs (the kind cluster
  is recreated each invocation).
- Test credentials in CI — none needed; the bot token is
  generated fresh per run.

**Acceptance criteria status:**
- [x] CI job green on a clean main branch (locally verified;
