# Helm chart + Central-side precondition docs

Status: ready-for-agent
Type: AFK

## What to build

A Helm chart that deploys the operator into a consumer MC, plus the
README documenting Central-side preconditions and the
NetworkPolicy/Secret-delivery patterns the operator deliberately does
not own.

Chart contents:

- Operator `Deployment` (single replica, runs in its own namespace,
  e.g. `tunnelport-system`).
- `ServiceAccount` + cluster-scoped read on `RemoteApp` and `Secret`,
  namespace-scoped writes on `Deployment`/`Service`/`ConfigMap` via a
  ClusterRole (so the SA can render across all namespaces).
- The CRD bundle from slice 1.
- Helm values for: `tbot.image` (single global version per consumer
  MC), `tbot.resources.requests` / `tbot.resources.limits` (cluster
  defaults; CR cannot override).
- Operator's own resource requests/limits as Helm values too.

Chart README documents:

- The operator does **not** create `RoleBinding`s granting
  create-`RemoteApp` to anyone — that's an explicit per-cluster
  decision.
- The operator does **not** render `NetworkPolicy` for the rendered
  *tbot pods*. Document the canonical pod labels
  (`tunnelport.giantswarm.io/role=tbot`,
  `…/remoteapp=<name>`) so the platform team's hand-written policy has
  a stable selector. tbot egress to `proxyAddr:443` and ingress from
  approved callers is the platform team's to enforce.
- The chart **does** render a `NetworkPolicy` for the operator's own
  *manager pod*, per GS kubebuilder-operator convention (default-deny
  with explicit allow rules for kube-apiserver egress and metrics
  ingress). This is operator hygiene, not tenant policy.
- Expected `tokenRef` Secret-delivery pattern (out-of-band via GitOps +
  sealed/sync). The operator never reads the Secret.
- Central-side preconditions per `RemoteApp`: a `TeleportBot` with a
  role whose `app_labels` matches exactly that one app, plus a static
  join token bound to that bot — produced by the upstream Teleport
  Operator on Central.
- The note from ADR 0002: rolling many `RemoteApp` Deployments
  simultaneously may briefly hit Central's join-rate limits.

## Acceptance criteria

- [ ] `helm install tunnelport ./chart` on a fresh kind cluster yields a running operator and registered CRD
- [ ] Operator RBAC matches what the design requires (no `pods/log`, no `Secret` *data* reads — only metadata watches)
- [ ] `tbot.image` and `tbot.resources` Helm values flow into rendered Deployments
- [ ] README documents the four operator-non-owned concerns (RBAC for the CR, NetworkPolicy, token delivery, Central-side preconditions)
- [ ] Chart values are `helm lint`-clean

### Agent Brief

**Category:** enhancement
**Summary:** Helm chart that deploys the operator into a consumer MC, plus a chart README documenting Central-side preconditions and the patterns the operator deliberately does not own.

**Current behavior:**
The operator can only be installed via raw manifests; no chart, no values surface, no documentation of operational preconditions.

**Desired behavior:**
`helm install tunnelport ./chart` on a fresh Kubernetes cluster
produces a running operator and a registered CRD. Helm values control
the tbot sidecar's image and resource requests/limits (cluster-wide
defaults — these are *not* fields on the CR) and the operator's own
image and resources. The chart README documents four operator-non-owned
concerns clearly enough that a platform engineer reading it for the
first time knows what they need to set up themselves.

**Key interfaces:**
- Helm values surface (top-level keys to expose):
  - `image` and `resources` for the operator container
  - `tbot.image` and `tbot.resources.requests` / `tbot.resources.limits` for the per-`RemoteApp` tbot sidecar
  - `installNamespace` (default `tunnelport-system`)
- Chart-rendered RBAC for the operator's `ServiceAccount`:
  - cluster-scoped `get`/`list`/`watch` on `RemoteApp` and on `Secret` *metadata only* (no `get` on Secret data)
  - cluster-scoped `get`/`list`/`watch`/`create`/`update`/`patch`/`delete` on `Deployment`, `Service`, `ConfigMap` (since the operator renders into arbitrary namespaces)
  - **no** `pods/log` — verifiable in the rendered manifests; enforced by ADR 0003
- Chart bundles the CRD from slice 1.
- Chart does **not** bundle any `RoleBinding` granting create-`RemoteApp` to anyone — per-cluster decision.
- Chart does **not** render `NetworkPolicy` for the rendered *tbot pods* (tenant resources). README documents the canonical pod labels (`tunnelport.giantswarm.io/role=tbot`, `tunnelport.giantswarm.io/remoteapp=<name>`) so platform teams have a stable selector for hand-written policies.
- Chart **does** render a `NetworkPolicy` for the operator's own *manager pod*, per GS convention — default-deny with explicit allow rules for kube-apiserver egress and metrics scraping ingress.
- Chart bundles the CRD at `templates/crds.yml` with `helm.sh/resource-policy: keep` and gated by `crds.install` (per GS convention; see `docs/gs-operator-conventions.md`). A `make update-helm-crds` target keeps it in sync from `config/crd/bases/`.
- `Chart.yaml` carries the `application.giantswarm.io/team: bumblebee` annotation. Chart publishes to `control-plane-catalog`. The manager pod template references the cluster-managed `gsoci.azurecr.io` pull-secret via `imagePullSecrets:` — the chart does not render the Secret itself. See the "Resolved choices" table in `docs/gs-operator-conventions.md`.

**Acceptance criteria:**
- [ ] `helm install tunnelport ./chart` on a fresh kind cluster yields a running operator and a registered CRD
- [ ] Operator RBAC matches the constraints listed under Key interfaces (no `pods/log`, no `Secret` data reads)
- [ ] `tbot.image` and `tbot.resources` Helm values flow into rendered tbot Deployments
- [ ] README documents the four operator-non-owned concerns: who can create `RemoteApp`s, NetworkPolicy, token Secret delivery, Central-side TeleportBot/role/token preconditions

- [ ] `helm lint` is clean

**Out of scope:**
- Generating any `NetworkPolicy` for the *rendered tbot pods* (tenant resources) — rejected during design. The operator-manager `NetworkPolicy` *is* in scope.
- Generating `RoleBinding`s that grant `RemoteApp` creation rights — left for each cluster's platform team.
- Multi-tenant RBAC profiles or values-templated tenant scoping.
- Per-`RemoteApp` overrides for image or resources — those stay cluster-wide.
