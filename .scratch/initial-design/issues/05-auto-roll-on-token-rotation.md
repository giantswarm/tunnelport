# Auto-roll on token Secret rotation

Status: ready-for-agent
Type: AFK

## What to build

The operator watches `Secret`s referenced by any `RemoteApp.spec.tokenRef`
and auto-rolls the corresponding tbot Deployment when the Secret's
content changes. Mechanism: stamp the Secret's `resourceVersion` onto
the pod-template annotation
`tunnelport.giantswarm.io/token-secret-version: <resourceVersion>`. The
Deployment's `RollingUpdate` strategy (already configured in slice 2)
handles the actual roll — `maxSurge: 1, maxUnavailable: 0` guarantees
no zero-pod window for new connections.

Watch is scoped to Secrets actually referenced by some `RemoteApp` —
unrelated Secret churn does not trigger reconciles. The operator
**never reads** the Secret's contents.

## Acceptance criteria

- [ ] Editing the referenced Secret's content triggers exactly one rolling restart of the tbot Deployment
- [ ] The pod-template annotation reflects the latest `resourceVersion` after each change
- [ ] Editing an unrelated Secret in the same namespace does not trigger a reconcile
- [ ] During the roll, the new pod must reach `Ready` (tunnel established) before the old pod is terminated
- [ ] Operator does **not** read the Secret's contents (verified by RBAC and code inspection)
- [ ] Unit/integration test exercises the watch → annotation update → roll sequence

### Agent Brief

**Category:** enhancement
**Summary:** Roll the tbot Deployment automatically when the referenced token Secret's content changes.

**Current behavior:**
Editing the referenced token Secret has no effect on running pods. The renewable cert tbot already holds keeps working until the bot identity is invalidated upstream.

**Desired behavior:**
When a `Secret` referenced by some `RemoteApp.spec.tokenRef` changes,
the operator stamps the Secret's current `resourceVersion` into a
pod-template annotation on the corresponding Deployment, which in turn
causes the standard `RollingUpdate` strategy (already configured in
slice 2) to roll the pods. Unrelated Secret changes (in the same
namespace or elsewhere) do not trigger reconciles or rolls.

**Key interfaces:**
- Pod-template annotation key:
  `tunnelport.giantswarm.io/token-secret-version`. Value: the Secret's
  `resourceVersion` at the time of the most recent successful reconcile.
- Watch on `Secret` resources, mapped back to affected `RemoteApp`s via
  a controller-runtime predicate / mapping function. Only Secrets
  actually referenced by some `RemoteApp.spec.tokenRef` should generate
  reconcile requests.
- The operator must read Secret **metadata** only (name, namespace,
  resourceVersion) — not the data field. RBAC must not include `get`
  on Secret data; `watch`/`list` on Secret metadata is sufficient.

**Acceptance criteria:**
- [ ] Editing the referenced Secret's content triggers exactly one rolling restart of the tbot Deployment
- [ ] The pod-template annotation reflects the latest `resourceVersion` after each change
- [ ] Editing an unrelated Secret in the same namespace does not trigger a reconcile (verified in tests)
- [ ] During the roll, the new pod must reach `Ready` (tunnel established) before the old pod is terminated — the slice-2 rolling strategy already enforces this; the test should confirm
- [ ] Operator does **not** read the Secret's contents (verified by RBAC and code inspection)
- [ ] Unit/integration test exercises the watch → annotation update → roll sequence

**Out of scope:**
- Reading or copying the Secret's contents anywhere in the operator code.
- Adding a status condition like `TokenSecretRotated` — rejected during design; the auto-roll is fast enough that the intermediate state isn't worth surfacing.
- Persisting the cert cache across pod restarts to avoid re-joins — see ADR 0002 (`emptyDir`, accept re-join on restart). Do not introduce a PVC or `StatefulSet` for this purpose.
