# Status reporting wired to pod state

Status: ready-for-agent
Type: AFK

## What to build

Populate `RemoteApp.status` from k8s-visible state only — no `pods/log`
RBAC, no log parsing (per ADR 0003).

- `status.ready`: true when at least one tbot pod is `Ready`. Pod
  readiness itself is wired to tbot's diag endpoint reporting tunnel
  state, so pod-`Ready` = tunnel-up.
- `status.lastError`: derived from pod `Phase`, `ContainerStatuses`,
  `RestartCount`, last termination reason. Strings like
  `"CrashLoopBackOff (5 restarts), last termination: Error (137)"`.
  Empty when ready.
- `status.observedGeneration`: standard kubebuilder pattern.
- `status.conditions`: `Ready` (mirrors pod readiness),
  `TokenSecretBound` (referenced Secret + key exist).

The reconciler watches owned `Deployment`/`Pod` events to refresh
status promptly, in addition to the periodic resync.

## Acceptance criteria

- [ ] `status.ready=true` only when a tbot pod is `Ready` *and* its readiness probe is configured to hit tbot's diag tunnel-state endpoint
- [ ] Missing token Secret → `TokenSecretBound: false`, pods stuck `Pending`, `lastError` reflects the volume-mount failure
- [ ] Crashlooping tbot → `Ready: false`, `lastError` reflects restart count and last termination reason
- [ ] Healthy steady state → `Ready: true`, `lastError` empty
- [ ] `observedGeneration` updates on every successful reconcile after a spec change
- [ ] Operator does **not** request `pods/log` RBAC (verified by inspecting the generated RBAC manifests)

### Agent Brief

**Category:** enhancement
**Summary:** Populate `RemoteApp.status` from k8s-visible state only, with no `pods/log` reads.

**Current behavior:**
The status struct exists on the type (slice 1) and the reconciler renders pods (slice 2), but `status` fields are never written.

**Desired behavior:**
- `status.ready` reflects whether at least one tbot pod is `Ready`,
  *and* the rendered pod's k8s readiness probe is configured to hit
  tbot's diag endpoint that reports tunnel state — so pod-`Ready` =
  tunnel-up, not just process-up.
- `status.lastError` is a short, k8s-derived string when not ready
  (e.g. `"CrashLoopBackOff (5 restarts), last termination: Error (137)"`)
  and empty when ready. It must come from pod metadata only — never
  from log content.
- `status.observedGeneration` follows the standard kubebuilder pattern.
- `status.conditions` carries `Ready` (mirrors pod readiness) and
  `TokenSecretBound` (true when the referenced Secret + key exist).

**Key interfaces:**
- `Ready` and `TokenSecretBound` as `metav1.Condition` types on the
  status conditions list.
- Reconciler watches owned `Deployment` and `Pod` resources so status
  refreshes on event, not just on the periodic resync.
- Pod readiness probe configuration in the rendered Deployment must
  point at tbot's diag tunnel-state endpoint (this slice owns wiring
  that probe; the Deployment renderer in slice 2 should be updated to
  configure it).
- The operator's generated RBAC must not include `pods/log` —
  enforced by ADR 0003.

**Acceptance criteria:**
- [ ] `status.ready=true` only when a tbot pod is `Ready` *and* its readiness probe hits tbot's diag tunnel-state endpoint
- [ ] Missing token Secret → `TokenSecretBound=false`, pods stuck `Pending`, `lastError` reflects the volume-mount failure
- [ ] Crashlooping tbot → `Ready=false`, `lastError` reflects restart count and last termination reason
- [ ] Healthy steady state → `Ready=true`, `lastError=""`
- [ ] `observedGeneration` updates on every successful reconcile after a spec change
- [ ] RBAC manifests do not contain `pods/log`

**Out of scope:**
- Tailing or parsing tbot logs into status — forbidden by ADR 0003. Do not introduce `pods/log` RBAC.
- Active probing of the rendered Service from the operator — rejected during design.
- A `certExpiry` field on status — rejected during design; if cert expiry monitoring is wanted later, scrape tbot's Prometheus metrics instead.
- Classifying errors into specific condition types beyond the two listed (`ProxyReachable`, `AppFound`, etc.) — rejected during design to avoid coupling to tbot log format.
