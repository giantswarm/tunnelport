# End-to-end smoke: real tbot, real Teleport, real producer

Status: ready-for-human
Type: HITL

## What to build

The tracer-bullet milestone: a workload pod in a kind consumer cluster
successfully `curl`s a `RemoteApp`'s Service and reaches a sample
producer app through real Teleport. Proves the design works end-to-end.

The HITL coordination required:

- Decide which Teleport instance backs the smoke test (cloud test
  tenant, or a locally-run Teleport binary in CI later).
- Provision a sample app on a producer kind cluster
  (`teleport-kube-agent` in app mode publishing a simple HTTP
  responder).
- Provision a `TeleportBot` + role + static join token on Central, with
  the role's `app_labels` matching the sample app.
- Deliver the join token Secret into the consumer kind cluster.

Then on the consumer side: deploy the operator, apply a `RemoteApp`
referencing the token, run a curl-pod that hits
`http://<service>:<port>` and verify the response comes from the
producer app.

### Human Brief

**Category:** enhancement
**Summary:** Set up the smoke-test environment proving the operator works end-to-end against real Teleport, and produce a runbook a developer can follow from zero to green.

**Current behavior:**
Operator code (slices 1–2) renders Kubernetes objects but has never been exercised against a real Teleport control plane.

**Desired behavior:**
A platform engineer can follow a runbook to bring up two kind clusters
(consumer + producer), provision a Teleport identity for the test,
deploy the operator and a sample `RemoteApp`, and `curl` from a pod in
the consumer cluster to a sample app served by the producer cluster,
succeeding.

**Why human-only (cannot be delegated to an AFK agent):**
- Choosing which Teleport instance backs the smoke (cloud test tenant
  vs locally-run binary) requires platform-engineer judgment about
  tenant management, credential handling, and Giant Swarm policy.
- Provisioning the `TeleportBot` + role + static token on Central
  depends on the upstream Teleport Operator being run by a separate
  team — coordination, not code.
- Token Secret delivery into the consumer kind cluster reflects the
  team's chosen secret-sync pattern (sealed-secrets, ESO, etc.) and
  must match what production uses.

**Key interfaces (where the design is locked):**
- The producer side is `teleport-kube-agent` in app mode publishing a
  simple HTTP responder; the consumer side is the operator + a sample
  `RemoteApp` whose `tokenRef` points at a Secret containing the static
  join token issued for the test bot.
- The tbot pod's k8s readiness probe must be wired to tbot's diag
  endpoint reporting tunnel state — this is the foundation slice 4
  builds on.

**Acceptance criteria:**
- [ ] Documented setup steps for the test Teleport instance (which one, credentials, how to access)
- [ ] Sample producer-kind manifests under `hack/smoke/producer/`
- [ ] Sample consumer-kind manifests under `hack/smoke/consumer/`
- [ ] Runbook at `hack/smoke/README.md` taking a developer from zero to green
- [ ] Curl-pod assertion succeeds; response body matches the producer's
- [ ] tbot pod readiness probe wired to tbot's diag tunnel-state endpoint

**Out of scope:**
- CI automation — that's slice 7.
- Failure-injection scenarios beyond curl-success.
- Database / Kubernetes / SSH access via Teleport — `RemoteApp` is scoped to Application Service apps only (see `CONTEXT.md`).
